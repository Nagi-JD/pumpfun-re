# `pump_fees` instruction-data frames, read from the deployed bytes

Anchor strips the 8-byte discriminator before the handler runs, so every handler works on a reader over the instruction bytes that follow it. This page records what each of the 31 deployed handlers does with that reader: where the reader comes from, the length gates the bytes are held to, and the byte offset and width of every load off the reader pointer. Generated by `tools/arg_frames.py`; the raw records are in `maps/pump_fees_arg_frames.json`.

Two reader regimes appear, and both are visible in the instruction stream:

* **handler frame** - the handler receives the caller frame pointer in `r5`, so the reader pointer is `[r5-0x1000]` and its length `[r5-0xff8]`. The handler loads the bytes itself.
* **deserialiser frame** - the handler stashes the reader pointer in a frame slot (`stxdw [fp+S], <reader ptr>`) and calls the generated argument deserialiser with `r2 = fp+S`, i.e. `&mut &[u8]` (pointer at `[r2]`, length at `[r2+8]`). The loads are in that frame and the handler reads the deserialised struct.

## What the bytes say

The 31 handlers split three ways: **13** load the fixed argument bytes in their own frame, **9** hand the reader to a generated deserialiser frame (the same frame is reused by every handler declaring the same argument list), **9** never touch the reader at all - those declare no arguments, and the absence of a load is the measurement that says so.

### Length gates

The gates are the same shape everywhere: `jeq rX, 0` when a single byte is read (a one-byte read only needs a non-empty reader), `jlt rX, N` when N bytes are taken at once, and the remainder is decremented between fields (`add64 rX, -N`) so the next gate is stated against what is left. In `get_fees` at `0x136c8` the gate is `jlt r1, 0x11` for the first 17 bytes and then `jlt r3, 0x8` on the difference, i.e. 25 bytes for the fixed part.

### `get_fees`: the third argument is length-checked but never loaded

`GetFees` declares `is_pump_pool: bool`, `market_cap_lamports: u128`, `trade_size_lamports: u64`, `is_new_quote_mint: OptionBool` - 26 bytes with the tag. The deployed code loads byte `0` (`ldxb r6, [r2+0]` at `0x136ac`), the 16 bytes at `1` and `9` (`ldxdw r4, [r2+1]`, `ldxdw r3, [r2+9]` at `0x136cd`/`0x136cc`) and the tag byte at `0x19` (`ldxb r1, [r2+0x19]` at `0x136d0`). Bytes `17..25`, the `u64`, are covered by the length gate and never read: the reader walks from the `u128` straight to the tag.

### `OptionBool` is optional on the wire

At `0x136cf` the deployed code compares the reader length with `0x19` and skips the tag load when it matches exactly (`jeq r1, 0x19, +0x4`): a 25-byte argument frame is valid and means "tag absent". A 26-byte frame supplies the tag at `0x19`, and the value is range-checked (`jeq 0` / `jne 1`) before use.

### Option arguments gate the payload, not the frame

`admin_cto_sharing_config` takes `new_admin: Option<Pubkey>`. The deployed code loads the tag at offset `0` (`ldxb r1, [r4+0]` at `0x139f0`), accepts only `0` or `1` (`jeq 1` at `0x139f3`, falling through to the error path otherwise) and, on the `Some` path only, requires 33 bytes (`jlt r0, 0x21` at `0x139f5`) before taking the pubkey at `1..33`. A one-byte frame with tag `0` is a complete instruction.

### Variable-length arguments: prefix, cap, stride

Every `Vec`/`String` argument starts with a `u32` length at the current reader position (`ldxw r1, [r9+0]` at `0x1f9a` for `FeeTier`, `0x212f` for `Shareholder`, `0x2027` for `String`), and the element count is capped before the allocation:

| argument | prefix | element stride | element cap | bytes | gate |
|---|---|---:|---:|---:|---|
| `vec<FeeTier>` | `u32` | 40 | 102 | 4080 | `0x1faa` / `0x1fad` |
| `vec<Shareholder>` | `u32` | 34 | 120 | 4080 | `0x2141` / `0x2144` |
| `String` | `u32` | - | - | 1048576 | `0x202e` |

The two vector caps are the same 4080-byte budget; they differ only because the element strides do: `FeeTier` is `u128` + `Fees` (`16 + 3*8 = 40`) and `Shareholder` is `pubkey` + `u16` (`32 + 2 = 34`), so both recover the declared struct sizes from the multiplier alone. `String` is capped at 1 MiB and is followed by the next field at a position the reader only knows at run time - `create_social_fee_pda` reads `platform` straight off the advanced reader (`ldxb r1, [r1+0]` at `0x13ab1`) after the shared deserialiser returns.

### Field loads are not one load per field

A 32-byte `Pubkey` arrives as an inlined copy: `initialize_fee_program_global` takes it with `ldxw r2, [r2+0]`, `ldxh r5, [r2+4]`, `ldxdw r1, [r2+6]`, `ldxb r4, [r2+0xe]`, `ldxdw r5, [r2+0x21]` and two more (`0x12e0d`-`0x12e1e`). Reading the frame as contiguous byte spans is what turns those fragments back into one `pubkey@0+32` followed by `disable_flags@32+1` and `claim_rate_limit@33+8` - the same offsets the declaration order gives, unaligned because Borsh does not pad.
